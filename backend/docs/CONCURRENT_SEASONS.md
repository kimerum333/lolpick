# v0.14.0: 동시 시즌·감사 로그·프론트 조회 연결

동시 시즌의 원장·감사 로그 구조와 DB 이관 절차를 설명한다. 코드 제공은 실제 DB 적용을 의미하지 않는다.

## 변경된 동작

- 기존 단일 포인트 거래 테이블을 유지한다. 새 지갑 테이블은 없다. 회원+시즌 거래 합계와 마지막 balance_after, 초기 지급 기록을 검증한다.
- members.current_points/current_season_id는 마지막 거래가 발생한 시즌의 호환용 캐시다. 사용자가 선택한 시즌이나 모든 시즌의 잔액을 뜻하지 않는다.
- 활성 시즌을 동시에 둘 수 있다. 초기 지급·베팅·정산·시즌 종료는 해당 시즌의 원장만 사용한다. 회원 잠금과 사용자 시즌→경기→세션→회원→응원계약 순서를 유지한다.
- 로그인 시 각 활성 비데모 시즌의 초기 지급을 한 번씩 확인한다. 기존 시즌의 지급·거래는 초기화하지 않는다. 복수 활성 시즌에서 /auth/me는 시즌을 자동 선택하지 않는다.
- /auth/me?season_id=...로 시즌을 선택한다. 선택하지 않았고 활성 비데모 시즌이 여러 개면 currentSeasonId=null, currentPoints=0이다. availableSeasonIds와 sessionExpiresAt을 반환한다. 하나면 기존 클라이언트와의 호환을 위해 그 시즌을 반환한다.
- 읽기 API는 원장을 만들지 않는다. 아직 초기 지급이 없는 활성 시즌은 해당 시즌의 initialPoints를 표시하고 실제 쓰기 트랜잭션에서 초기 지급한다. 완료된 지급으로 오해하지 않도록 프론트는 이 값으로 거래 성공을 단정하지 않는다.
- JSONL 파일 보존·outbox 재처리·속도 제한·관리자 MFA·DB TLS 검증 등 v0.12 보안 수정을 로컬 코드와 통합했다. 로그 context.archive_file의 DB CHECK 불일치를 수정했다.
- 응원 선택, 베팅, 기존 포인트 원장 유일성, 고정 6시간 세션 규칙을 유지한다. 표시용 캐시 또는 API 조회로 세션을 연장하지 않는다.
- 수집기는 누락된 팀 표시 필드와 시즌의 기존 display_data를 보존한다. 시간당 수집 설정은 변경하지 않았다.

## 신규 조회 API

모든 경로의 접두사는 /api/v1이다. 기존 경로와 쿼리의 엄격한 검증도 유지한다.

| 경로 | 응답과 접근 |
|---|---|
| GET /events/{event_id} | 기존 SeasonOut + stages. 현재 단계는 공급자 round별 첫/마지막 경기 시작 시각, 경기 수, 시각 미정 경기 수를 집계한다. 정식 운영 단계의 종료 시각을 뜻하지 않는다. |
| GET /matches/{match_id}/stake-ranking | 팀별 최대 5명, 순서·금액·팀 풀 대비 shareBasisPoints·봉인 상태. 회원/인증/Google/거래 식별자는 공개하지 않는다. displayName은 정책 미확정으로 null이다. |
| GET /auth/matches/{match_id}/context | 인증 필수·no-store. 해당 시즌 잔액, 내 응원·베팅·팀별 내 순서(myRank), 참여 조건·사유, 기존 세션 만료시각. 향후 베팅 성공을 보장하는 예약 API는 아니다. |

## 기존 응답 확장

- GET /events 및 /seasons: year=2000..9999 필터, startsAt/endsAt 밀리초 타임스탬프. 배열 계약 유지.
- GET /teams: 시즌 미지정 시 모든 활성 시즌의 팀 합집합. 임의 첫 시즌을 선택하지 않는다.
- GET /matches: date=YYYY-MM-DD는 한국 시간의 해당 일자 [00:00, 다음 날 00:00). unscheduled=true는 시각 미정만 조회. 두 조건을 함께 보내면 422. 기존 limit 상한 100 유지.
- GET /matches/{id}: bettingClosedReason 추가. 기존 시작 시각 마감 기준을 유지한다. 디자인 샘플의 10분 전 마감은 요구 확정 전 적용하지 않았다.
- POST /auth/bets: 성공·멱등 재전송 응답에 현재 해당 시즌 잔액과 응원 스냅샷 추가. 원래 베팅 필드는 유지. 커밋 실패 시 성공 응답을 보내지 않는다.
- 인증 헤더 또는 쿠키가 포함된 응답도 no-store. 공유 정상 캐시를 새로 켜지 않았다. 장애 대체 캐시의 응답은 bettingOpen=false와 cached_snapshot 사유를 표시한다.

## DB 적용 자료

- 현재 리비전: 0010_concurrent_seasons. 필요 사전 리비전: 0009_user_actions.
- 기존 DB: docs/concurrent-seasons-upgrade.sql(단독 트랜잭션) 또는 Alembic upgrade head 중 하나를 선택한다. 둘 다 반복 적용하지 않는다.
- 이미 0008이면 먼저 기존 0009 절차를 거치거나 Alembic 체인을 사용한다. 실제 revision 확인 전 SQL을 실행하지 않는다.
- 빈 DB 초기화 SQL은 docs/schema.sql이다. 기존 DB에 실행하지 않는다. 기존 원장·회원·세션·이력은 삭제하거나 재작성하지 않는다.
- 마이그레이션은 시즌→경기→회원→원장 순서로 쓰기를 잠시 막고 현재 원장·회원 캐시를 사전 검증한다. 잠금/실행 시간이 상한을 넘거나 불일치가 있으면 트랜잭션 전체를 실패시킨다. 데이터 자동 수리는 없다.
- 신규 함수나 역할 권한을 추가하지 않는다. 기존 trusted migration owner 소유 post_point_entry를 교체하며 런타임의 직접 포인트/관리자 쓰기 권한을 열지 않는다.
- 운영 적용 전 백업과 격리 PostgreSQL 검증이 필요하다. 가상 데이터 검증 성공으로 PostgreSQL 검증을 대체하지 않는다.

## 남은 작업

- 공개 닉네임 정책과 최소 DB 컬럼/수정 권한. 현재 공개 순위의 이름은 null이다.
- 디자인 전용 브랜드·분류·정식 단계 관계와 경기 매핑. 현재 round 집계는 연결 준비용이다.
- 정상 공개 조회 캐시·프론트 요청 재사용·배포 자산 캐시·성능 측정. 부하 장치의 적용으로 오해하지 않는다.
- 고유 계정 전환/로그아웃 시 Vue 개인 캐시 제거, 실제 OAuth·TLS·권한·동시성 검증.
- 라이엇을 포함한 제3자 사이트의 스트레스 테스트, 의도적 부하, 대량·병렬 호출과 제한 우회는 금지한다. 부하 검증은 우리가 통제하는 격리 테스트 환경에서만 한다.

## 폴더 구성

runtime: 애플리케이션·실행 의존성·배포 예시만. maintenance: 테스트·문서·마이그레이션·검증 자료. 원래 .env, .venv, logs, 운영 데이터와 비밀값은 포함하지 않는다. 런타임에 마이그레이션 실행 자료를 복사할 필요가 없다.

## v0.14 잠금 정비

시즌 활성화와 등록 사이의 회원 스냅샷은 advisory shared/exclusive gate로 보호합니다.
로그인은 gate→활성 시즌(정렬)→등록 신원→세션→회원, 내 정보는 세션→회원 순서입니다.
수집·정산·종료는 해당 시즌만 잠급니다. 공급자 writer gate는 유지하며 배팅은 이 gate를 사용하지 않습니다.
잠금 획득 시 ORM 기존 객체를 재조회해 만료/철회/시즌 상태의 오래된 값을 승인 조건으로 사용하지 않습니다.
현재 API 페이지는 API_GUIDE.html, 실제 연결 코드는 frontend-api.ts입니다.
